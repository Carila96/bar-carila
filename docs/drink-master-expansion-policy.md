# Bar Carila ドリンクマスター拡張・推薦方針

Version: 1.0
Established: 2026-09-07

## 1. 最上位原則

Bar Carila のドリンクマスターは、推薦可能な酒の上限を定めるホワイトリストではない。

- 既知マスターに存在する酒は、名称・別名・レア度・説明・レシピ等を安定して補完するために積極的に利用する。
- 既知マスターに存在しない酒も、推薦条件に最も合うなら推薦してよい。
- 「マスターにない」という理由だけで候補から除外してはならない。
- マスターは継続的に拡張する。現在の400杯は完成数ではなく初期母集団である。

運用は **Open Recommendation + Growing Known Master** とする。

## 2. 推薦とマスター登録を分離する

推薦エンジンの目的は、その利用者・その夜の条件に最も適した一杯を選ぶこと。マスターの目的は、既知の酒について正規化された安定情報を提供すること。この2つを混同しない。

1. 推薦時はマスター内外を問わず候補を考える。
2. 推薦酒が既知マスターに一致すればマスター情報で補完する。
3. 一致しなければ未知酒として推薦を成立させ、未登録をエラー扱いしない。
4. 未登録酒は登録基準を満たす場合に将来の拡張候補とする。

## 3. 新規登録の最低条件

- 実在する飲料・カクテルとして確認できる。
- 既存 masterKey・日本語名・英語名・主要aliasとの重複を確認する。
- 日本のBARでの提供可能性を評価できる。
- 特殊材料が必要ならその特殊性をレア度へ反映する。
- カクテルは再現可能な標準レシピまたは妥当な代表レシピを確認する。
- 出典不明のAI生成名称や実在確認できない創作酒を自動登録しない。

## 4. 登録時の必須情報

既存スキーマを正とし、可能な限り以下を揃える。

- canonical masterKey
- 日本語表示名 / canonical name
- 英語名・主要別名・表記揺れ（aliases）
- category
- rarity / rarityLabel
- evidenceVersion / evaluatedAt
- description
- trivia（妥当な情報がある場合）
- recipe（カクテル等で必要な場合）
- 画像検索に利用できる識別情報

既存フィールド名・型は実装側スキーマを優先し、この文書だけを理由に互換性を壊さない。

## 5. 日本BAR基準のレア度評価

レア度は「世界に存在するか」ではなく、主として **日本の一般的なBARで注文した際に提供できる可能性** を評価する。

材料の入手性を見るのは、それ自体を目的とするためではない。BARで実際に提供可能かを推定するための一要素として扱う。

評価時には以下を総合する。

- 日本のBARでの認知・掲載・提供実績
- ベーススピリッツや主要材料の一般性
- 特殊リキュール、特殊ワイン、地域限定材料、生鮮材料等の必要性
- 標準的なBAR設備で再現できるか
- 名称を伝えた際にレシピが通じる程度の定着度
- 日本国内で材料を現実的に調達できるか

単一サイトや単一メニューだけで断定せず、既存の rarity evidence / research 文書と同等以上の検証粒度を維持する。

## 6. 追加優先順位

杯数を増やすこと自体をKPIにしない。重複や低品質データで水増ししない。

1. 推薦で実際に登場したマスター外の酒
2. 既存400杯の明確なカテゴリ・味・ベース・地域の空白を埋める酒
3. 日本のBARで一定の提供可能性がある定番・準定番
4. 世界的に確立しているが日本ではやや珍しい酒
5. 特定条件の利用者に有用なニッチな酒

未知酒が推薦された事実だけで無条件に自動登録しない。実在性・重複・レシピ・レア度を検証してから登録する。

## 7. 拡張単位と変更管理

- 原則としてバッチ単位で追加し、追加数・対象範囲・調査日を記録する。
- evidenceVersion を更新する場合は、何を再評価した版なのかを明記する。
- 既存酒の masterKey は安易に変更しない。名称変更・alias追加で吸収できる場合は互換性を優先する。
- 既存レア度を変更する場合は、変更理由と根拠を残す。
- 追加後は validator / tests を通し、重複・欠損・alias衝突・件数不整合を確認する。
- D1とembedded masterを併用する期間は、どちらが正とされるかを実装上明示し、無断でsource-of-truthを反転させない。

## 8. 推薦速度改善時の禁止事項

速度改善のためであっても、以下は禁止する。

- 既知マスター内だけに推薦候補を閉じる。
- マスター外候補を低評価にするだけの恣意的ペナルティを加える。
- 速度のために酒名の多様性・適合性を意図せず落とす。
- 未知酒を既知酒へ無理に近似して別の酒として表示する。

速度改善では「候補空間を狭める」のではなく、推薦判断と文章生成の分離、既知情報の高速補完、キャッシュ、段階表示等を優先する。

## 9. 将来の拡張フロー

1. 候補収集
2. 既存マスターとの重複・alias照合
3. 実在性・標準名称・代表レシピ確認
4. 日本BARでの提供可能性調査
5. rarity判定と根拠記録
6. masterKey・各フィールド作成
7. validator / tests
8. Preview確認
9. Production反映

このフローを通したものだけを「既知マスター」と呼ぶ。

## 10. 現在の方針

- 現在の400杯を既知マスターとして維持する。
- 推薦候補は400杯に限定しない。
- 400杯外の良い推薦を許容する。
- 既知マスターは上記ルールに従って継続拡張する。
- 高速化実装は、このOpen Recommendation方針を壊さないことを受入条件とする。
